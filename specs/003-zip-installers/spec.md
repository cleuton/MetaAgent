# Feature Specification: Linux Zip Distribution

**Feature Branch**: none. No branch is created. All work stays on the current branch; `003-zip-installers` is only the name of this feature's folder under `specs/`.

**Created**: 2026-10-02

**Status**: Draft

**Input**: User description: "Generate one zip, Linux AMD64 only, containing the binary, the examples, metagente.toml and the docs (README.md, guide.md, syntax.md, tutorial.md). Docs in a docs folder, examples in a samples folder, binary in a bin folder. A small README.md at the zip root with the version, how to run the program from bin, and how to put it on the PATH or in /usr/local/bin. Build instructions for Windows and macOS go into the repository's main README.md. Nothing more."

## Scope

One deliverable: `dist/metagente-linux-amd64.zip`, generated by the agent. This distribution is version v0.1.1, and the version changes everywhere the project keeps it: the main `README.md`, `Cargo.toml` (and `Cargo.lock`, updated by the build) and `CHANGELOG.md`. The main `README.md` also gains a new section with the instructions and the small README templates needed to produce the Windows and macOS zips by hand. One housekeeping line: `dist/` in `.gitignore`. That is the whole feature.

Out of scope: zips or binaries for Windows and macOS, scripts of any kind, package formats, cross compilation, checksums, any version change other than the v0.1.1 change listed in D-4, CI, new files anywhere else in the repository.

## Decisions (already made; do not ask)

- **D-1, zip layout**: a single top folder `metagente/` (so unzipping never scatters files), containing exactly:
  - `README.md` (the small one, per FR-003)
  - `metagente.toml` (the basic commented file from the repository root)
  - `bin/metagente` (the release binary)
  - `docs/README.md`, `docs/guide.md`, `docs/syntax.md`, `docs/tutorial.md` (the repository `README.md` and the three files from `docs/`, copied as they are; the copied `README.md` therefore includes the "Building the Windows and macOS zips" section, which is redundant inside the zip and accepted on purpose; its relative links to `docs/` and `examples/` may not resolve from inside the zip, also accepted)
  - `samples/` with exactly these five files from the repository `examples/` folder: `clock.ag`, `read_file.ag`, `weather.ag`, `planner.ag`, `remote_weather.ag`. The `broken_*` and `cycle_*` test files stay out, and the `samples/city-briefing` project stays out (it needs an API key and its own setup).
- **D-2, how it is built**: after applying the D-4 version change and writing the FR-004 section in the main `README.md`, the agent runs `cargo build --release` (plain glibc binary) and the system `zip` command directly, assembling the staging folder in a temporary location outside the repository and writing `dist/metagente-linux-amd64.zip`. Before starting, it checks that `cargo`, `zip`, `unzip` (used by FR-002 to verify the zip) and `objdump` (binutils, used by FR-003) exist; if one is missing, it stops and says which one and how to install it, instead of improvising with another tool. When the zip is verified, it deletes the staging folder. No script is created or left behind.
- **D-3, the small `README.md`**: for Linux, written by the agent during assembly from the content fixed in FR-003, existing only inside the zip. For Windows and macOS, its text lives as a plain text template inside the FR-004 section. No script, in the repository or in the README, generates it.
- **D-4, version v0.1.1 everywhere**: this distribution is version v0.1.1, matching the project's own rule that the version is kept in the main `README.md`, in `CHANGELOG.md` and in `Cargo.toml`. The agent makes exactly these version changes, BEFORE building, so the binary prints the new version: (1) in `README.md`, the line `**Version: v0.1.0**` becomes `**Version: v0.1.1**`; other mentions of `v0.1.0` in the README are history and stay; (2) in `Cargo.toml`, `version = "0.1.0"` becomes `version = "0.1.1"`; (3) in `CHANGELOG.md`, the heading `## Unreleased` becomes `## v0.1.1 - 2026-10-02` and one line is added at the end of its "Added" list: `- Distribution as a zip for Linux AMD64, and instructions in the README to build the Windows and macOS zips.`; (4) `Cargo.lock` is changed only by `cargo build` itself, which updates the `metagente` package entry to 0.1.1 on its own; the agent does not edit it by hand; (5) in `README.md`, the sentence in the "Versioning" section that says the version is kept in this file, in `CHANGELOG.md` and "(once it exists)" in `Cargo.toml` is rewritten, because it is out of date: it becomes "Semantic versioning. The version is kept in this file, in `CHANGELOG.md` and in `Cargo.toml`." Nothing else about versions changes. Creating the git tag `v0.1.1` is done later by the maintainer, by hand, on the commit that holds these changes; the agent never creates it (D-6).
- **D-5, repository changes**: the implementation changes exactly five files: `README.md` (the version line and the "Versioning" sentence per D-4, and one new section per FR-004), `Cargo.toml` and `Cargo.lock` (version only, per D-4), `CHANGELOG.md` (per D-4) and `.gitignore` (the single line `dist/`). The Speckit artifacts of this feature are saved normally and are not implementation changes: `specs/003-zip-installers/` (spec, plan, tasks and related files) and the update of `.specify/feature.json` to point at `specs/003-zip-installers`.
- **D-6, git**: the agent runs no git command that changes state: no add, commit, tag, branch or push. Committing is the maintainer's job.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Unzip and use (Priority: P1)

A person downloads `metagente-linux-amd64.zip`, unzips it into any folder, opens a terminal and follows the small `README.md`. Metagente runs. They install nothing else.

**Independent Test**: on a Linux machine without Rust or Metagente, unzip, follow only the `README.md` at the zip root, and run the named sample.

**Acceptance Scenarios**:

1. **Given** the unzipped `metagente/` folder, **When** the user runs `./bin/metagente --version` in it, **Then** `metagente 0.1.1` is printed.
2. **Given** the unzipped folder, **When** the user runs `./bin/metagente run samples/clock.ag now`, **Then** the Clock agent answers with the time.
3. **Given** a user who follows the `README.md` note on the PATH (or on copying to `/usr/local/bin`), **When** they open a new terminal, **Then** `metagente --version` works from any folder.

### User Story 2 - Build the Windows and macOS zips by hand (Priority: P2)

On a Windows machine or a Mac with Rust installed, the maintainer opens the repository's main `README.md`, follows the new section top to bottom, copy and paste, and produces `metagente-windows-amd64.zip` or `metagente-macos-arm64.zip` with the same layout as D-1 (on Windows, `bin/metagente.exe`). Nothing in the section requires writing anything from memory.

**Acceptance Scenario**:

1. **Given** the new `README.md` section, **When** the maintainer follows its steps on the other platform, following each step and copying the README template as given, **Then** the resulting zip has the D-1 layout and its small `README.md` differs from the Linux one only in the platform specific lines.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The agent first applies the D-4 version change and writes the FR-004 section in the main `README.md`, so the `README.md` copied into the zip (D-1, `docs/README.md`) already carries the new version and the section; only then does it build the release binary, assembles the D-1 layout in a staging folder, removes any previous `dist/metagente-linux-amd64.zip`, and zips the folder as `dist/metagente-linux-amd64.zip` with `zip -r -D` (`-D` leaves out the folder entries, so the zip holds only files), so a re-run replaces the artifact instead of appending to it.
- **FR-002**: Before zipping, the agent runs `./target/release/metagente --version` and proceeds only if it prints exactly `metagente 0.1.1`; if it prints anything else, the agent stops and reports it, and does not edit any file outside the D-5 list to make it match. After zipping, it lists the zip's contents and confirms they match D-1 exactly, and that `bin/metagente` keeps its executable permission inside the zip (for example with `unzip -Z`), because a binary that unzips without it fails with "Permission denied".
- **FR-003**: The small `README.md` at the zip root fits on one screen and says only:
  - what Metagente is, in one sentence, and the version `v0.1.1` (D-4);
  - how to run it from the unzipped folder: `./bin/metagente --version`, then the sample `./bin/metagente run samples/clock.ag now` (Windows: `.\bin\metagente.exe` with backslashes), with one line saying the other samples are reading material and may need extra setup described in `docs/tutorial.md`;
  - how to make it available everywhere: on Linux and macOS, add the `bin` folder to the PATH or copy `bin/metagente` to `/usr/local/bin`, with the exact commands; on Windows, one line pointing to adding the `bin` folder to Path in Settings, under "Edit environment variables", with no command;
  - which systems it serves, stated honestly: the agent reads the highest glibc version the binary requires (`objdump -T` on the binary) and writes the real minimum, never an assumed one; the Windows and macOS templates state 64 bit Windows and Apple Silicon macOS;
  - on Windows and macOS only, one honest line about the first run of an unsigned downloaded binary: SmartScreen may warn ("More info", then "Run anyway"); Gatekeeper may block, and `xattr -d com.apple.quarantine bin/metagente` clears the quarantine. No instruction ever disables security features globally. The Linux README carries no such line;
  - where the full docs are: `docs/` in the zip, and the repository, `https://github.com/cleuton/MetaAgent`.
- **FR-004**: The repository's main `README.md` gains one new section, "Building the Windows and macOS zips", written as plain instructions for a person, NOT as a script. The steps of the section MUST NOT contain any shell block that creates, copies, deletes or generates files: no `mkdir`, `cp`, `rm`, `Remove-Item`, `cat`, heredoc or similar sequence, and no command that writes a README. This prohibition applies only to the assembly steps of the section; it does not apply to the text of the README template in (c), which legitimately contains commands the end user will run later (for example `export PATH=...`, `sudo cp bin/metagente /usr/local/bin/`, `xattr -d com.apple.quarantine bin/metagente`). For each of the two platforms (Windows, macOS) the section contains exactly, in this order: (a) the one prerequisite, Rust from rustup.rs (on Windows, add one plain sentence: the Rust installer may ask for the Visual Studio C++ build tools; accept it; this is text, not a second prerequisite); (b) numbered steps in plain sentences: open a terminal in the repository root folder (macOS: in the Finder, right click the folder and choose "New Terminal at Folder", which can be turned on under System Settings, Keyboard, Keyboard Shortcuts, Services, Files and Folders; Windows: in File Explorer, click the address bar, type `powershell` and press Enter) and run `cargo build --release` (a one line command); create a folder `metagente` inside `dist/` (creating `dist/` first if missing; it is gitignored), deleting any previous `metagente` folder and old zip there first; build inside it the folder tree, which the section itself reproduces in a plain text block (the D-1 layout, with `bin/metagente.exe` on Windows); copy the files into it as the section's own two column list says, one row per file, source path relative to the repository root on the left and destination path inside `metagente/` on the right (a list to read, not commands), with exactly these rows: the release binary (`target/release/metagente`, on Windows `target\release\metagente.exe`) to `bin/metagente` (on Windows `bin\metagente.exe`); `metagente.toml` to `metagente.toml`; `README.md` to `docs/README.md`; `docs/guide.md`, `docs/syntax.md` and `docs/tutorial.md` each to the same name under `docs/`; `examples/clock.ag`, `examples/read_file.ag`, `examples/weather.ag`, `examples/planner.ag` and `examples/remote_weather.ag` each to the same name under `samples/`; create `README.md` at the top of the `metagente` folder with the content of the template in (c), checking that the file name ends in `.md` and not `.md.txt` (on Windows, in Notepad choose "All files" in "Save as type"); and zip the `metagente` folder into `dist/` named `metagente-windows-amd64.zip` or `metagente-macos-arm64.zip`. The zip step is: on macOS, open a terminal in the `dist/` folder the same way ("New Terminal at Folder" on `dist/`) and run the one line command `zip -r -D metagente-macos-arm64.zip metagente` (the Finder's Compress is not used, because it adds `__MACOSX` and `.DS_Store` entries that break the D-1 layout); on Windows, File Explorer: Windows 11, right click the folder and choose "Compress to ZIP file"; Windows 10, or Windows 11 under "Show more options", right click, "Send to", "Compressed (zipped) folder"; then rename the zip. The section MUST be self-contained: a person who reads only this section, without this spec or any other document, has the tree, the file list, the commands and the README template in front of them, and nothing in the steps refers to this spec, to D-1 or to any text outside the section. The only command lines in the section's steps are `cargo build --release` and, on macOS, the one line `zip` command. (c) the full text of that platform's small `README.md`, as a plain text block labeled "content of README.md", with the version already written as `v0.1.1` and everything else already written, including that platform's security line and PATH note per FR-003. It is file content to copy into a new file, not a step.
- **FR-005**: Besides the Speckit artifacts allowed by D-5, the only repository changes are the five files listed in D-5, each changed only as D-4, FR-004 and D-5 describe.

## Success Criteria *(mandatory)*

- **SC-001**: A person on a clean Linux machine goes from downloaded zip to a working `./bin/metagente --version` in under 2 minutes, using only the `README.md` at the zip root. The agent cannot time a person: it checks that every step of that README works when followed literally (FR-002 and the unzip run in the tasks), and says in its final report that the 2 minutes were not measured.
- **SC-002**: One run of the agent leaves `dist/metagente-linux-amd64.zip` ready to distribute, with no manual step.
- **SC-003**: The maintainer produces the Windows or macOS zip using only the FR-004 section, following its steps and copying its README template, writing nothing from memory. The section's steps contain no script.
- **SC-004**: After the run, the implementation changes in `git status` are only the five files in D-5 (`README.md`, `Cargo.toml`, `Cargo.lock`, `CHANGELOG.md`, `.gitignore`); the Speckit artifacts (the `specs/003-zip-installers/` folder and the updated `.specify/feature.json`) are the only other things. The version reads v0.1.1 in the README, in `Cargo.toml`, in the `CHANGELOG.md` heading, in the output of `./bin/metagente --version` and in the zip's `README.md`. No script, and no commit, tag or branch created by the agent.
