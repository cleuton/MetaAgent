# Project Constitution: Metagente

**Version**: 1.0.0 | **Ratified**: 2026-09-05 | **Last Amended**: 2026-09-05

## Preamble

Metagente is an interpreted fourth generation language (4GL) built for a single purpose: letting anyone, with little or no prior programming experience, build working AI agents in minutes. The interpreter is written in Rust. The language speaks MCP (Model Context Protocol) and A2A (Agent to Agent) natively, and ships with a set of built in tools ready to use from the very first program.

This constitution defines the non negotiable principles that guide every design decision for the language, the interpreter, and the tooling around it. Every spec (spec.md), plan (plan.md), or task list (tasks.md) generated by Speckit for this project must respect these principles. When a principle and a feature requirement conflict, the principle wins, unless this constitution is amended first.

## Core Principles

### I. Radical simplicity above everything

Metagente is a 4GL. That means the user describes WHAT the agent should do, not HOW to do it. Every syntax decision must be judged against one question: "can a beginner read this out loud and understand what happens?" If the answer is no, the syntax is rejected.

Concrete rules:
* No feature may require prior knowledge of object oriented programming, pointers, manual memory management, or explicit concurrency.
* No mandatory ceremony. A minimal working agent fits in under 10 lines.
* Syntax and runtime errors must produce natural language messages, pointing at the exact line and suggesting a fix, never a raw Rust interpreter stack trace.
* The language does not adopt design patterns, layered architectures, or abstraction layers as a prerequisite for use. If a concept requires explaining a design pattern before teaching the basic syntax, the concept is wrong, not the explanation.

### II. The agent is the primary unit of execution

Everything in Metagente revolves around the `agent` block. There are no classes, low level modules, or namespaces exposed to the end user as a prerequisite. An `.ag` file defines one or more agents, and each agent has a declared goal (`goal`), a set of enabled tools (`tool`), and message or task handlers.

Rationale: a 4GL for AI agents needs the domain's central concept (the agent) to also be the language's central concept, with no mental translation between "what I want to build" and "what I write."

### III. Interoperability through MCP and A2A is not optional

Every agent written in Metagente is, by default, an MCP client capable of discovering and invoking tools exposed by external MCP servers, and can also expose its own tools as an MCP server for other clients. Calling an MCP tool and executing a task through it must be a single high level instruction in the language, without requiring the user to manually handle handshakes, JSON schemas, or transport details (stdio, HTTP, or SSE).

Every agent also speaks A2A: it publishes its own Agent Card, can be discovered by other agents (including agents outside the Metagente ecosystem), and can start tasks on remote A2A compatible agents using the same syntax used to call a local MCP tool.

No future version of the language may remove MCP and A2A or downgrade them to background features requiring external libraries. They are part of the core.

### IV. Built in tools, with no friction

The interpreter ships, with no additional installation, a minimal set of native tools: file access (read and write), HTTP requests, environment variables, a simple state store (the agent's short term memory), and a basic clock or scheduler. Enabling a built in tool is a single line (`tool file`, `tool http`). New built in tools only enter the core if they satisfy Principle I, and more specialized tools should be distributed as external MCP packages instead of bloating the language core.

### V. Dynamic agent to agent invocation (dynamic link)

A Metagente agent can invoke another agent, also written in Metagente, through a dynamic link mechanism: the calling agent references the target agent by name or path at runtime, and the interpreter resolves, loads, and executes that agent on demand, without the calling agent needing to know its implementation at compile time or write time. This is distinct from A2A: dynamic link is the native, local (same host, same runtime, or a compatible runtime) way of composing Metagente agents, while A2A is the protocol for composing with remote agents, possibly written in other languages or frameworks.

Rule: an agent's public interface (the messages or tasks it accepts) must be described in a clear section of its own `.ag` file, so that a dynamic link call can be validated before execution and produce a natural language error on mismatch.

### VI. Rust as the execution foundation

The interpreter is written in Rust, prioritizing memory safety, no garbage collector with unpredictable pauses, and good performance for concurrent I/O (MCP and A2A calls are mostly asynchronous). The interpreter core does not depend on a heavy virtual machine or an external managed runtime. Rust ecosystem libraries (tokio for async, serde for serialization) may be used freely; what must never happen is Rust's complexity leaking through to the Metagente end user.

### VII. Declarative and readable syntax before expressive syntax

When a more expressive or powerful syntax conflicts with a more readable and predictable one, readability wins. Metagente prioritizes predictability and a single obvious way to do each common thing, over multiple flexible ways to do the same thing.

## Additional Constraints

* **Portability**: the interpreter must compile and run on Linux, macOS, and Windows from the same Rust source, with no platform forks.
* **Secure by default**: file access, network access, and dynamic link invocation of other agents must respect an explicit per agent permission model (the agent declares what it needs to access), so an agent cannot silently read files or call the network outside what it declared.
* **Open protocols**: MCP and A2A implementations must follow the public specifications of the respective protocols, with no proprietary extensions that break compatibility with third party clients or servers.
* **Simple packaging**: a Metagente agent and its dependencies (other dynamically linked agents, declared external MCP tools) must be distributable as a single folder or file, with no need for a complex package manager for the simplest use cases.

## Development Workflow

* Every new language feature starts as a specification (spec.md) via Speckit, describing behavior from the point of view of the person writing agents, before any Rust implementation decision.
* No feature is accepted into the core without at least one complete example of an `.ag` agent demonstrating its use, written as if for a beginner.
* Changes to the language grammar require updating the parser, at least one working example, and the syntax documentation in the same pull request.

## Governance

This constitution takes precedence over any development practice, technical plan, or individual style preference. Amendments require:

1. Explicit record of the change and its motivation.
2. Verification that existing specs, plans, and task lists do not become inconsistent with the change (or updating them).
3. Version increment following semver: MAJOR for removal or backward incompatible redefinition of a principle, MINOR for adding a principle or new material section, PATCH for clarifications and wording fixes.
